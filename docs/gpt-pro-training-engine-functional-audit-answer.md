## Bottom-line verdict

The repository **does contain a real local Dart training engine** that uses completed **strength** sets to update e1RM history, fatigue impulses, daily load/ACWR, and load recommendations. Those outputs are wired into the active workout suggestion card, watch snapshot payload, dashboard heatmap, dashboard readiness card, and debug surface.

However, it is **not functionally mature enough to trust without caveats**. The highest-risk issues are:

1. Completed-workout sync into the engine is **fire-and-forget** and can fail silently.
2. Saved engine state **short-circuits re-bootstrap from app history**, so failed syncs and profile changes may not self-heal.
3. HealthKit ingestion is **partial/source-present**, and the initial provider path can replace missing/denied HealthKit data with **demo sleep/HRV records**.
4. Load recommendations do **not use routine target reps/RPE** in the visible active workout path.
5. Timed exercises are modeled in the app but effectively **ignored by the engine**.
6. The UI can label a reduced/deloaded recommendation as “hold steady” because direction is derived from performance delta, not the actual suggested weight or safety gate.

## 2. Data-flow trace: completed workout set → engine state → user-visible output

1. **User logs a strength set.**
   In the active workout UI, strength input uses weight, reps, optional comment, and RPE modal. The log button calls `WorkoutController.logSet(weightKg, reps, note, rpe)`. Evidence: `lib/src/features/workout/active_workout_screen.dart`; `lib/src/features/workout/workout_controller.dart`.

2. **The app stores an app-level `CompletedSet`.**
   `WorkoutController.logSet` creates a `CompletedSet` with `exerciseId`, `setNumber`, `weightKg`, `reps`, `completedAt`, note, and RPE. Evidence: `lib/src/features/workout/workout_controller.dart`; model in `lib/src/data/models/completed_set.dart`.

3. **The user completes the session.**
   `WorkoutController.completeSession` marks the session completed, sets `endedAt`, sets session RPE fallback, calls `_syncTrainingEngine(updatedSession)` without awaiting it, persists the session, and advances routine-group state. Evidence: `lib/src/features/workout/workout_controller.dart`.

4. **The adapter maps app session → engine session.**
   `TrainingEngineAdapter.toEngineSession` filters to sets with `reps > 0`, clamps RPE to 5–10, marks missing set RPE as estimated, and returns an `EngineSession`. Timed sets with `reps == 0` are excluded. Evidence: `lib/src/features/training_engine/training_engine_adapter.dart`.

5. **The controller mutates and saves engine state.**
   `TrainingEngineController.ingestSession` loads the engine, calls `engine.ingestSession(session)`, saves `engine.serializeState()`, and invalidates `trainingEngineProvider`. Evidence: `lib/src/features/training_engine/training_engine_controller.dart`; repository in `lib/src/features/training_engine/training_engine_state_repository.dart`.

6. **The engine updates multiple subsystems.**
   `TrainingEngine.ingestSession` groups sets by exercise, selects a heaviest top set, computes e1RM, appends e1RM history, computes muscle fatigue impulses if the exercise is in the registry, appends daily volume load, updates ACWR EWMA, stores last top set, and increments `sessionsIngested`. Evidence: `packages/training_engine/lib/src/engine.dart`; formulas in `packages/training_engine/lib/src/e1rm/*.dart`, fatigue in `packages/training_engine/lib/src/fatigue/*.dart`, ACWR in `packages/training_engine/lib/src/acwr/*.dart`.

7. **Visible output path A: active workout suggestion.**
   `engineWeightSuggestionProvider` loads the engine and calls `engine.recommendLoad(exerciseId)`, then `TrainingEngineUiAdapter.toWeightSuggestion`. The active workout screen reads this provider and renders `_ProgressionHint`; it also uses the suggested weight as fallback prefill if no current or previous app set exists. Evidence: `lib/src/features/training_engine/training_engine_provider.dart`; `lib/src/features/training_engine/training_engine_ui_adapter.dart`; `lib/src/features/workout/active_workout_screen.dart`.

8. **Visible output path B: dashboard heatmap.**
   `MuscleHeatmapCard` reads `liveEngineHeatmapDataProvider`, which returns persisted engine fatigue or projected active-workout fatigue from `engine.previewFatigueWithSets`. The UI adapter maps engine muscle IDs to body heatmap muscles. Evidence: `lib/src/features/dashboard/muscle_heatmap_card.dart`; `lib/src/features/training_engine/training_engine_provider.dart`; `lib/src/features/training_engine/training_engine_ui_adapter.dart`.

9. **Visible output path C: dashboard readiness.**
   `TrainingReadinessCard` reads `readinessProvider`, which calls `engine.computeReadiness()`. Readiness uses ACWR plus sleep/HRV if present; the card separately displays max muscle fatigue from `engine.fullFatigueMap()`. Evidence: `lib/src/features/dashboard/training_readiness_card.dart`; `lib/src/features/training_engine/training_engine_provider.dart`; `packages/training_engine/lib/src/readiness/*.dart`.

10. **Visible output path D: watch snapshot.**
    `WatchSyncService._buildSessionSnapshot` reads `engineWeightSuggestionProvider` for routine exercises and includes `suggestedWeightKg` in the watch payload. Evidence: `lib/src/features/watch/watch_sync_service.dart`.

11. **Notable separate path: Progress screen.**
    Progress PR/e1RM analytics use `ProgressService` over app sessions and the exported `compositeE1rm` formula, not the engine’s persisted rolling state. Evidence: `lib/src/features/progress/progress_service.dart`.

## 3. Data-flow trace: Apple Health / sleep / HRV → engine readiness → user-visible output

1. **The app has a HealthKit-enabled flag.**
   `AppState` stores `healthKitEnabled`. The attached source verifies the flag, but not the settings UI that toggles it. Evidence: `lib/src/data/models/app_state.dart`.

2. **HealthKit source requests authorization and fetches records.**
   `HealthKitDataSource` is iOS-gated through `defaultTargetPlatform == TargetPlatform.iOS`. It requests read access for sleep-asleep/deep/REM/light, HRV SDNN, and resting heart rate. It returns empty lists when authorization fails, HealthKit is unavailable, samples are empty, or errors occur. Evidence: `lib/src/features/training_engine/healthkit_data_source.dart`.

3. **Initial engine load fetches HealthKit data if the flag is enabled.**
   `loadTrainingEngine` calls `healthKit.fetchRecentSleep()` and `fetchRecentHrv()` when `appState.healthKitEnabled` is true. Evidence: `lib/src/features/training_engine/training_engine_provider.dart`.

4. **Problem: initial load falls back to demo recovery data.**
   If both fetched lists are empty, `loadTrainingEngine` uses `DemoSeedData.seedSleep()` and `DemoSeedData.seedHrv()`. Evidence: `lib/src/features/training_engine/training_engine_provider.dart`; `lib/src/data/seed/demo_seed_data.dart`.

5. **Engine stores sleep and HRV records.**
   `TrainingEngine.ingestSleep` and `ingestHrv` append records and trim histories. `TrainingState` persists `sleepHistory`, `hrvHistory`, and `lastHealthKitFetch`. Evidence: `packages/training_engine/lib/src/engine.dart`; `packages/training_engine/lib/src/models/training_state.dart`.

6. **Readiness provider refreshes stale HealthKit data.**
   `readinessProvider` calls `engine.refreshHealthKitIfStale`, saves the engine state, and returns `engine.computeReadiness()`. Evidence: `lib/src/features/training_engine/training_engine_provider.dart`; `packages/training_engine/lib/src/engine.dart`.

7. **Pure engine computes readiness.**
   `computeReadiness` scores sleep with `scoreSleep`, HRV with `scoreHrv`, ACWR via `currentAcwr`, and blends available sources. Evidence: `packages/training_engine/lib/src/engine.dart`; `packages/training_engine/lib/src/readiness/sleep_scorer.dart`; `packages/training_engine/lib/src/readiness/hrv_scorer.dart`; `packages/training_engine/lib/src/readiness/composite_readiness.dart`.

8. **Dashboard displays readiness.**
   `TrainingReadinessCard` displays score, limited-data message when not full tier, latest sleep, latest HRV, max fatigue, and last-sync footer when `lastHealthKitFetch` exists. Evidence: `lib/src/features/dashboard/training_readiness_card.dart`.

**Conclusion for this flow:** the pure engine can use HealthKit-style sleep/HRV data, and the app has a source-level HealthKit fetch path. But production truth is weaker: native runtime is unverified here, the settings toggle UI is not in this archive, denied/no-data/error are indistinguishable from empty data, and initial empty HealthKit fetch can be replaced with demo records.

## 4. Concrete bugs and suspicious gaps

1. **Engine sync can be lost permanently.**
   `completeSession` calls `_syncTrainingEngine` with `unawaited`, catches failures only by logging, and persists the session anyway. Then `loadTrainingEngine` returns restored saved state without reconciling app history. Evidence: `lib/src/features/workout/workout_controller.dart`; `lib/src/features/training_engine/training_engine_provider.dart`; `lib/src/features/training_engine/training_engine_controller.dart`.

2. **Saved engine state ignores updated app profile fields.**
   `loadTrainingEngine` creates a new engine from `adapter.toUserProfile(appState)`, but then `restoreState(savedState)` replaces the engine state and returns immediately. Also, the adapter currently ignores `AppState.age`, `AppState.weight`, and `AppState.fitnessGoal`. Evidence: `lib/src/features/training_engine/training_engine_provider.dart`; `lib/src/features/training_engine/training_engine_adapter.dart`; `lib/src/data/models/app_state.dart`.

3. **HealthKit empty data becomes demo data on initial load.**
   Empty HealthKit sleep/HRV lists fall back to `DemoSeedData.seedSleep()` and `seedHrv()`. Since `HealthKitDataSource` returns empty on denial, unavailable platform, no samples, or errors, this can create fake readiness data. Evidence: `lib/src/features/training_engine/training_engine_provider.dart`; `lib/src/features/training_engine/healthkit_data_source.dart`; `lib/src/data/seed/demo_seed_data.dart`.

4. **HealthKit refresh clears old data and may repeatedly fetch on empty results.**
   `refreshHealthKitIfStale` replaces sleep and HRV histories with fetched lists and stamps `lastHealthKitFetch` only when at least one list is non-empty. The provider saves that state. Evidence: `packages/training_engine/lib/src/engine.dart`; `lib/src/features/training_engine/training_engine_provider.dart`; `packages/training_engine/test/engine_test.dart`.

5. **Visible load recommendations do not use the routine’s target reps.**
   Active workout asks only for `engineWeightSuggestionProvider(exerciseId)`. The provider calls `engine.recommendLoad(exerciseId)` with no overrides. The engine then uses movement-class defaults from `TargetParams.defaultFor`, while seeded routines have their own `RoutineExercise.targetReps`. Evidence: `lib/src/features/workout/active_workout_screen.dart`; `lib/src/features/training_engine/training_engine_provider.dart`; `packages/training_engine/lib/src/engine.dart`; `packages/training_engine/lib/src/progression/performance_delta.dart`; `lib/src/data/seed/demo_seed_data.dart`.

6. **UI direction can mislabel deloads/reductions.**
   `buildRecommendation` returns `PerformanceDelta.maintenance` for deload, reduce-load, maintain, and suggest-alternative safety-gate outcomes. `TrainingEngineUiAdapter` maps `maintenance` to “hold,” regardless of suggested weight reduction or gate action. Evidence: `packages/training_engine/lib/src/progression/recommendation.dart`; `packages/training_engine/lib/src/progression/safety_gates.dart`; `lib/src/features/training_engine/training_engine_ui_adapter.dart`; `lib/src/features/workout/active_workout_screen.dart`.

7. **Timed exercises do not affect the engine.**
   Timed sets are stored with `reps: 0`, `weightKg: 0`, and `durationSeconds`. The adapter and live preview provider filter to `reps > 0`. Evidence: `lib/src/features/workout/workout_controller.dart`; `lib/src/features/training_engine/training_engine_adapter.dart`; `lib/src/features/training_engine/training_engine_provider.dart`.

8. **RPE scale mismatch.**
   App `CompletedSet` documents RPE as 1–10, and the active workout slider allows 1–10. Engine `LoggedSet` rejects RPE below 5, so the adapter clamps lower values to 5. Evidence: `lib/src/data/models/completed_set.dart`; `lib/src/features/workout/active_workout_screen.dart`; `lib/src/features/training_engine/training_engine_adapter.dart`; `packages/training_engine/lib/src/models/logged_set.dart`.

9. **ACWR is not true daily aggregation.**
   Engine ingestion appends one `DailyLoad` per ingested session and updates EWMA per session. `updateEwma` normalizes dates but still applies the load every call, including same-day calls. Evidence: `packages/training_engine/lib/src/engine.dart`; `packages/training_engine/lib/src/acwr/ewma.dart`; `packages/training_engine/lib/src/models/daily_load.dart`.

10. **e1RM top set is selected by heaviest weight, not best e1RM.**
    `TrainingEngine.ingestSession` picks the heaviest set with reps as tiebreaker before computing e1RM. Evidence: `packages/training_engine/lib/src/engine.dart`. A lighter higher-rep set can produce a higher e1RM estimate than the heaviest set.

11. **Smart Planner is not adaptive to current fatigue/readiness/history.**
    Smart Planner uses the training-engine registry/planner functions, but its controller does not read `trainingEngineProvider`, e1RM, fatigue, ACWR, sleep, or HRV. Evidence: `lib/src/features/smart_planner/smart_planner_controller.dart`; `lib/src/features/smart_planner/planner_registry_adapter.dart`; `packages/training_engine/lib/src/planner/session_generator.dart`.

12. **Progress analytics are not using engine rolling state.**
    `ProgressService` computes PRs/e1RM directly from app sessions using exported `compositeE1rm`, not `TrainingEngine.currentE1rm` or `TrainingState.e1rmHistory`. Evidence: `lib/src/features/progress/progress_service.dart`.

13. **Watch suggestions are source-present but initialization is unverified in this archive.**
    `WatchSyncService` includes engine suggested weights in watch snapshots, but the file says `initialize()` must be called once during app initialization and the attached archive does not show that call. Evidence: `lib/src/features/watch/watch_sync_service.dart`.

14. **Heatmap drops unmapped canonical muscles.**
    `TrainingEngineUiAdapter._muscleMap` does not map every muscle in `defaultMuscles`; unmapped entries are skipped. Evidence: `lib/src/features/training_engine/training_engine_ui_adapter.dart`; `packages/training_engine/lib/src/fatigue/muscle_registry.dart`.

15. **Readiness flags are under-implemented.**
    `ReadinessFlag` includes acute sleep deprivation and rising resting HR, but `computeReadiness` only adds ACWR danger and cold-start flags. Sleep and HRV scorers apply penalties internally but do not expose those flags. Evidence: `packages/training_engine/lib/src/readiness/composite_readiness.dart`; `packages/training_engine/lib/src/readiness/sleep_scorer.dart`; `packages/training_engine/lib/src/readiness/hrv_scorer.dart`.

## 6. Can we honestly say the app has a training engine based on previous sets plus Apple Health data?

**Yes, but only with strong caveats.**

A precise honest statement would be:

> The app includes a local Dart training engine that uses completed strength sets to compute e1RM estimates, localized fatigue, daily load/ACWR, readiness inputs, and load recommendations. The app also contains source-level HealthKit-style sleep/HRV models, scoring, and an iOS HealthKit data source that can feed readiness when `healthKitEnabled` is true.

What would be overstated:

> “The app has trustworthy production-ready recommendations based on previous sets plus Apple Health data.”

That is not fully supported by the attached sources because HealthKit runtime behavior is unverified, empty/denied HealthKit can become demo data on initial load, engine sync can fail silently, saved engine state does not reconcile with app history, routine-specific targets are not used in visible recommendations, and timed exercises are excluded from the engine.
