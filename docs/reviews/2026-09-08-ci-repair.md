# TestFlight CI repairs

The `v1.0.31+310` release run passed all 314 app tests and 489 engine tests, then failed both heatmap golden comparisons by 450 pixels (0.09%). The native and upload jobs did not run.

The diagnostic workflow run `34217580619` reproduced the same failure on macOS 15 ARM64 with Flutter 3.41.9. Its captured images show that all differing pixels are within the fixture captions at x286–506, y2–14. Every heatmap pixel matches the reference. The same Flutter version and architecture pass locally on macOS 27; setting `CI=true` locally does not reproduce the failure.

The fixture requested bold Ahem, although the bundled test font only provides regular weight. Synthetic bold and fractional font metrics made the caption edges depend on macOS text rasterization.

An initial correction used regular Ahem at integer glyph bounds. It passed locally but the `v1.0.31+312` CI run still differed by 288 caption-edge pixels. The new CI images again showed zero differing heatmap pixels: even regular Ahem remained dependent on the macOS text renderer.

The final fixture keeps front/back labels in semantics and paints only the component under test. `BodyHeatmap` itself paints paths, not text. The original 17-pixel label slots and the heatmaps' y25 starting position are unchanged. Both labels retain semantic assertions, and the whole-image comparison remains exact: no tolerance, skips, masks or cropping.

Both local golden tests pass with the corrected references. Pixel comparisons against the committed build310 references and the actual CI312 images show zero heatmap changes. All changed pixels are inside the fixture's original 17-pixel label slot. No production source changed.

CI now uploads golden failure images as verification artifacts. A manual `quality_only` option runs the same checks without signing or uploading, and generated failure images are ignored by Git.

Local diagnostic evidence is under `build/ci-repair-310/`: `ci-original-diff.json`, `ci-312-diff.json`, `phase2-pixel-verification.json`, the CI images, and reproduction/verification logs. The correction was released as `v1.0.31+313`; the failed tags remain unchanged.

## Paired Watch preferences

Run `34219360201` passed the exact golden comparisons, all app/package/native unit tests, all 11 iPad UI scenarios, and the phone UI, native wiring, Firestore rules, invite/auth, startup and persistence-restart suites. The paired Watch host driver failed at its first snapshot read with `Cannot read the Watch cache plist (1)`, so signing and upload were skipped.

The Watch was open on its idle screen. Its initial preferences can contain Health authorization state before a workout snapshot arrives. The host reader treated a missing cache key as pending only when `plutil` wrote one exact English diagnostic to stderr; every other nonzero result failed immediately and discarded the diagnostic. The captured CI error cannot distinguish a missing key from another extraction failure.

The host now reads binary/XML plists with Python's standard `plistlib`, once per poll. An absent file or key remains pending. Malformed plists, unreadable files, incorrect types and invalid snapshot JSON fail with a diagnostic. Health authorization retains integer/boolean types. Actual snapshot comparisons, the 25-second receipt deadline, stability windows, prior-session idle guard and visible Watch UI assertions remain enforced.

Regression tests cover binary/XML snapshots, startup preferences without a snapshot, absent files/keys, corrupt data and wrong types. These tests run in the existing CI helper-test step. The repair changes test infrastructure only; the next candidate is `v1.0.31+314`.

A fresh local paired run reached a real snapshot and the expected Watch UI, then exposed two existing short host deadlines: initial Watch installation exceeded 10 seconds, and the persisted Health result was still pending after 5 seconds. Installation now has a bounded 60-second timeout; other simctl commands retain 10 seconds and report the timed-out operation. Timed-out simctl processes are killed. Health observation waits up to 25 seconds for status 1/2 and pending=false; it does not synthesize or grant authorization. The receipt deadline and UI requirements are unchanged.

The next local run passed the complete Watch transport scenario and observed native Health status 2. In the following app scenario, the workout was visible in the screenshot, but AXe returned only the clock/status bar after the host reinstalled the same Watch app. The driver now installs the companion once per Flutter driver run and foregrounds that installation for the second scenario. Both scenarios still reset their receipt guard and verify the real expected snapshot and accessible workout UI.

Local verification: driver analysis and all 44 Python tests pass. One fresh paired run passed the full transport scenario, then failed after redundant installation in the app UI scenario. A subsequent run with one installation failed earlier at Watch reachability, before snapshot checks. A complete local paired pass is therefore not established for this candidate; the pinned macOS 15/Xcode 26.3 CI gate remains authoritative before upload. Local evidence is in `build/ci-repair-314-local*` and `build/ci-repair-310/paired-314-*`.

## CI duration

The user requested shorter CI after observing 245.5 seconds for CocoaPods and 352.4 seconds for Xcode before the iPad tests started. The previous successful iPad suite itself took 3m24s. It repeats the same eleven application UI scenarios already executed on iPhone, in iPhone-compatible mode; it is not a separate iPad product target.

Build 315 makes iPad compatibility checks opt-in (`run_ipad=true` on manual Build iOS dispatch). Full iPhone and paired Watch verification remains mandatory before TestFlight upload. Optional iPad execution is bounded at 25 minutes; the phone/Watch step at 45 minutes. Dependency caches are keyed by lockfiles and the pinned toolchain, with verified CocoaPods reused by the release job. Application builds and signing material are not cached. Runner artifacts now record setup and per-suite elapsed seconds. Cache savings require an eligible warm cache; no timing improvement is claimed before a measured run.
